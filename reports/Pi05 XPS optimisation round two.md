# Cut tokens and steps, not kernels

The runtime layer is finished: the remaining gains for the team's π0.5 on the XPS come from running it asynchronously on the arm, feeding it fewer prefix tokens, and taking fewer expert steps. The team's own sweep showed that no GPU-plugin setting beats the defaults, the kernel profile showed only 10.7 ms of launch gaps, and the GatedMLP build is worth about 2 ms. Three levers remain that are each worth tens of milliseconds or more. Asynchronous execution with Real-Time Chunking makes the current 140 ms largely invisible and takes hours, not days. Dropping the `inspect` camera from the policy input and retraining the expert removes 256 of 832 prefix tokens, an estimated 30 ms or more for roughly one 50-minute retrain. SnapFlow one-step distillation removes a further ~21 ms from the 5-step export. Stacked, the estimates point to roughly 80–100 ms per chunk, but every one of those figures is an extrapolation that must be measured. Further quantisation (static W8A8, INT4), any NPU placement, and another runtime are not worth the time. Before any of it, three checks gate the work: a GPU-versus-CPU parity run on real frames, a first π0.5 rollout on the arm, and a robot check of whether the INT8 jerk and the few-step range shrinkage matter at all. The fine-tune was only ~2,300 updates, so more training is likely worth more task success than any latency item here.

## Three checks come before any further speed work

**Parity on real frames is the first job, and it takes about half an hour.** Nota AI reports that on the same iGPU family the default settings "gave wrong prefix outputs on OpenVINO 2026.4", and it compiles its prefix with `GPU_ENABLE_SDPA_OPTIMIZATION=NO` ([Nota AI card](https://huggingface.co/geonmin-kim/nota-pi05-libero-vtp-drift-openvino)). The team measured that setting as 39 ms (22%) slower, so it must not be adopted on faith ([kernel README](../deploy/pi05/kernel/README.md)). The team's accuracy harness compares every variant against the FP16 export on the same GPU, so it cannot detect an error shared by all GPU variants. The check is to run the FP16 IR on CPU, on GPU with defaults, and on GPU with SDPA optimisation off, on the same held-out frames and the same noise, and compare all three with the PyTorch checkpoint. If GPU-default matches CPU, the warning does not apply to this export and the fast path stays. If only SDPA-off matches, the honest latency is about 39 ms worse and every plan below shifts. The same pass should confirm that fresh Gaussian noise is fed per chunk at deploy time: in-graph noise on the GPU plugin returned biased or repeated values in two independent reports, and external noise raised Nota's success from 90.5% to 94.0% ([Nota AI card](https://huggingface.co/geonmin-kim/nota-pi05-libero-vtp-drift-openvino)).

**The second check is a robot rollout.** π0.5 has not run on the arm, and the ACT policy that did run would not grasp. The one quantitative SO-101 benchmark puts fine-tuned π0.5 at **56% average success, with grasp instability and repetition loops in 91% of failed trials each** ([SO-101 benchmark](https://arxiv.org/html/2606.08881)). Those are execution failures, not latency failures. Every published add-on recipe trains far longer than this checkpoint did: 20,000–30,000 steps for SnapFlow, training-time RTC and VLASH, against ~2,300 here ([SnapFlow](https://arxiv.org/html/2604.05656v2); [LeRobot π0.5 docs](https://github.com/huggingface/lerobot/blob/main/docs/source/pi05.mdx)). A longer expert fine-tune is therefore the most probable route to a working grasp, and it should be the base for every retrain proposed below.

**The third check settles two open quality questions on the arm.** INT8 weights raise jerk from 1.18 to 2.85, and 5 steps cut motion range to 0.86 of recorded in FP16 ([opt README](../deploy/pi05/opt/README.md)). No published study measures whether either matters for success. One quantisation paper found that offline action error does not predict closed-loop success at all ([LoopQ](https://arxiv.org/html/2611.05093)). Comparing commanded and observed joint traces for one INT8 and one FP16 rollout shows directly whether the servos filter the jitter out.

Two smaller measurement gaps are cheap to close. The variants were timed in a contended round, where INT8 measured 200 ms against 174 ms idle, so the 140 ms figure should be re-timed on an idle machine, one process per export. The per-sub-graph profile exists only for the 200-token, 10-step graph, so the recommended export deserves its own profile before anyone budgets against it.

## Where the research notes lose to the team's measurements

Several hypotheses in the notes conflict with what the team measured, and the measurements win.

The quantisation note ranks a dynamic-quantisation group-size sweep first and names dynamic activation quantisation as the likely cause of the INT8 jitter. That experiment is done and the hypothesis is not supported. One detail matters for how the result is quoted. The kernel study found that the opt harness's bit-identical "DQ off" output came from a shared cache directory that served the default blob. With a fresh cache, turning dynamic quantisation off moves actions by 0.47° MAE and leaves the error against FP16 at +3.1%, against +3.3% for the default on the same frames ([kernel README](../deploy/pi05/kernel/README.md)). Either way the weights carry the error, and the variant with an FP16 expert and INT8 prefix has the same jerk, so the source is the **prefix weights**. Jerk under genuinely disabled dynamic quantisation is not tabulated; it is a ten-minute re-run with a per-config cache directory if anyone wants the last doubt removed.

The same note, and the earlier report, state that dynamic quantisation is skipped on the 50-token expert. The profile shows 740 DynamicQuantize kernels running there, and lowering the threshold variable changed nothing. The note's suggestion to test that threshold is therefore closed.

The earlier report called SDPA-off "worth one A/B run"; it is 22% slower and is now only a correctness fallback. It also estimated SnapFlow at about 80 ms from a third-party 9 ms per step. The measured step is **5.3 ms**, so one step saves 48 ms from the 10-step export and about 21 ms from the recommended 5-step one.

The prefix note asks the team to check whether the last Gemma layer's unused output is still computed. The profile already answers it: 17 Gemma SDPA kernels, with the 18th layer producing only K/V, and the prefix K/V computed once and reused across steps. There is nothing to recover. The note's linear estimates also assume 82 ms for an 832-token prefix, but 82 ms was measured at 968 tokens, so its absolute figures are slightly high. Against that, the 64-token change removed 136 tokens and saved 33–38 ms, more than linear scaling predicts, so token cuts on this GPU pay at least what the estimates say.

The runtime note points out that Intel quotes 153 GB/s peak memory bandwidth for this platform class, which would put the expert's 107 GB/s at about 70% of peak, not the 80% in the kernel study ([Intel OEP article](https://docs.openedgeplatform.intel.com/dev/_sources/OEP-articles/publications/optimizing-pi0.5-lva-model.md.txt)). The XPS memory speed is unverified. The conclusion holds either way: no system setting raises bandwidth, and only fewer bytes or fewer steps help.

### Run it asynchronously before optimising it further

Real-Time Chunking has the strongest evidence of anything in the notes. On real π0.5 robots at 5 denoising steps it showed **no degradation with up to 200 ms of injected delay**, while synchronous execution degraded linearly ([RTC paper](https://arxiv.org/html/2506.07339v2)). Even naive asynchronous execution beat synchronous on an SO-101 with π0.5, 89.7% against 83% ([VLASH](https://arxiv.org/html/2512.01031v1)). At 30 Hz, 140 ms is 4.2 control steps, so an inference delay of 5–6 with a new chunk requested every 8–12 executed actions is a sound start. The RTC paper clipped guidance weight at 5 for 5-step sampling because higher weights diverged. Physical AI Studio implements RTC with a gradient-free correction whose parameters are graph inputs, so the export must be made with RTC enabled; whether Studio's runtime ships an asynchronous executor for exported models is unclear and needs checking ([Studio rtc.py](https://github.com/open-edge-platform/physical-ai-studio/blob/main/library/src/physicalai/policies/mixins/rtc.py)). Temporal ensembling is the wrong tool: it oscillated into protective stops on real π0.5 robots ([RTC paper](https://arxiv.org/html/2506.07339v2)). RTC continues whatever the previous chunk contained, so it carries INT8 jitter forward and does not remove it.

System hygiene belongs with this step because the live loop differs from the benchmark. The xe driver has no waitboost, so a burst arriving after idle depends on the GuC ramp ([xe_guc_pc.c](https://raw.githubusercontent.com/torvalds/linux/v7.0/drivers/gpu/drm/xe/xe_guc_pc.c)). Raising `min_freq`, setting the performance profile and reading `freq0/throttle/reasons` during a run cost minutes ([kernel docs](https://docs.kernel.org/7.0/gpu/xe/xe_gt_freq.html)). Nobody has published the effect on inference, so sample `act_freq` across a live burst first. The measured lever is contention: the same export went from 174 to 201 ms when another job started, so keep browsers, video decode and other GPU clients off the iGPU during the demo.

### Two cameras is the cheapest large latency cut

Removing a camera cuts 256 prefix tokens and one of three SigLIP passes. The linear estimate is a prefix about 31% cheaper and vision about 7 ms cheaper, roughly 30 ms per chunk; the 64-token result suggests the real saving is larger. NVIDIA's π0.5 export drops unused camera slots for exactly this reason ([TensorRT Edge-LLM](https://nvidia.github.io/TensorRT-Edge-LLM/0.11.0/developer_guide/models/pi05.html)). The condition is absolute: **retrain the expert on two views, never mask a view at inference.** Masking the wrist camera on a π0.5 LIBERO checkpoint without retraining dropped success from 98.4% to 4.6% ([camera ablation](https://github.com/chaoshengsc/libero-camera-ablation)). The backbone stays frozen, so the retrain is the recipe the team has already run. The risk is task-specific. The pick instruction ends with holding the brick in front of the inspection camera, and the policy may use that view to position it. A two-camera retrain needs a go/no-go on the arm; if it fails, a small fixed token budget for `inspect` is the softer variant, with no direct evidence.

A learned fixed-K selector is the follow-on. VLA-ACL trains a small scorer with the VLA frozen, keeps 64 of 256 tokens per view, and reports **96.1% against 96.9% on π0.5 LIBERO with a 2.2× faster prefill**, in a few GPU-hours with public code ([VLA-ACL](https://arxiv.org/html/2610.08133v2)). Nota's K=128 sampler took 175 ms to 117 ms on an Arc B390 at about 2 points of LIBERO-10 ([Nota AI card](https://huggingface.co/geonmin-kim/nota-pi05-libero-vtp-drift-openvino)). Fixed K keeps shapes static, so one IR still works. Neither result is on an expert-only fine-tune or on INT8 weights, and porting it costs about a day, so it ranks below the camera drop.

### One-step distillation is worth ~21 ms and carries a known risk

SnapFlow fits this checkpoint: it freezes the VLM, trains only the expert, and Physical AI Studio ships it with a `--weights_from` path and OpenVINO export ([Studio how-to](https://github.com/open-edge-platform/physical-ai-studio/blob/main/library/docs/how-to/training/snapflow_distillation.md)). Two independent LIBERO runs match the 10-step teacher, 98.75% against 97.75% and 97.55% against 97.05% ([SnapFlow](https://arxiv.org/html/2604.05656v2); [Studio report](https://github.com/open-edge-platform/physical-ai-studio/blob/main/library/docs/explanation/benchmark/snapflow-libero.md)). Two cautions apply. The Studio guide warns that "distilling an undertrained phase-1 model just distills noise", and this teacher had ~2,300 updates. The student's target is the model's own two-step endpoint, and the team already measures range shrinking as steps fall; no source reports the amplitude of a distilled student. Motion range against recorded demos must be a release gate, and a 2-step export is a cheap hedge, since the paper's student has its lowest offline error at 2–3 steps. Guided RTC and one-step sampling probably conflict, because the guidance is applied across denoising steps. The compatible variant is training-time RTC, which LeRobot v0.7.0 ships for π0.5 and Studio does not ([LeRobot RTC docs](https://huggingface.co/docs/lerobot/en/rtc)). The combination is untested anywhere.

If the range shrinkage shows on the arm before distillation is ready, solver changes are the cheap fallback. A multistep solver such as Adams-Bashforth 2 reuses the previous velocity at no extra cost, and a non-uniform time grid is a one-line change; both need only a re-export. Heun and midpoint double the cost per step and are pointless here. None of this has π0.5 evidence.

### The jitter fix is a ten-minute bisect

Published work says INT8 weights are nearly lossless on π0.5: 0.15–0.21% action error offline, and 86% against 84% on a real Franka ([LoopQ](https://arxiv.org/html/2611.05093); [VLAQuantBench](https://arxiv.org/html/2609.25376)). The team's +3.9% is about twenty times that, so one block is probably responsible. `nncf.compress_weights` accepts an `ignored_scope`, runs data-free from the saved FP16 IR in about ten minutes, and avoids the 54 GB export. The order to try is SigLIP in FP16, then the projector, then `INT8_ASYM`, then Gemma attention projections in FP16 as QuantVLA does ([QuantVLA](https://arxiv.org/html/2602.20309v4)). The team's two profiles put FP16 vision at 25.1 ms against 22.1 ms, so the first variant costs about 3 ms. If the bisect finds nothing, a zero-phase low-pass over each chunk's arm joints, leaving the gripper untouched, is the execution-side fallback; no study validates it.

## What to leave alone

**Static W8A8 is not worth a second attempt.** The GPU plugin already runs INT8 activations on the FCs, the DynamicQuantize kernels cost only 5.7% of GPU time, and NNCF calibrates on CPU only, which is why the first run took 65 minutes and died ([nncf engine.py](https://raw.githubusercontent.com/openvinotoolkit/nncf/develop/src/nncf/openvino/engine.py)). The ceiling is a few percent with a real chance of breaking SDPA fusion.

**INT4 is a memory optimisation that this 64 GB machine does not need.** A cross-hardware π0.5 study concluded "quantization makes π0.5 smaller, not faster", and 4-bit weights dropped a real Franka pick task from 84% to 62% ([LoopQ](https://arxiv.org/html/2611.05093); [VLAQuantBench](https://arxiv.org/html/2609.25376)). The 4304-wide SigLIP layer that raised the group-size error is fixable with `ignored_scope`, but there is no reason to fix it.

**The NPU does not shorten a synchronous chunk.** Nota's heavily tuned NPU expert takes 77.8 ms for 10 steps, against the team's 53 ms on the iGPU, and its end-to-end NPU path is slower, 154 ms against 117 ms ([Nota NPU card](https://huggingface.co/wjwjwjwj/nota-pi05-libero-ae-npu-openvino); [Nota AI card](https://huggingface.co/geonmin-kim/nota-pi05-libero-vtp-drift-openvino)). A vision encoder on the NPU cannot run in parallel with anything inside one chunk. Present any NPU split as a power experiment.

**Caching and training-free pruning carry closed-loop risk for small gains.** Reusing prefix K/V across steps scored 0/1 and 0/2 on π0.5, and a frozen wrist frame scored 0/500 ([CrossVLA](https://arxiv.org/pdf/2605.21854); [camera ablation](https://github.com/chaoshengsc/libero-camera-ablation)). Cache gates on another VLA failed silently ([The Gate, Not the Cache](https://www.alphaxiv.org/abs/2608.00391)). In-LLM pruners give 1.25–1.27× on π0.5 at a higher accuracy cost than a learned selector ([APS-VLA](https://arxiv.org/html/2611.13030)).

**Layer dropping and depth distillation are real but multi-day.** Dropping 9 of 18 Gemma blocks holds LIBERO success at 57.9% of FLOPs, but only after a 30,000-step full fine-tune; nobody has shown it with a frozen backbone ([DTR](https://arxiv.org/html/2606.27755v1)). Do not truncate SigLIP, which loses about 11 points even after recovery.

The rest is quickly dismissed. Sub-224 resolution has no π0.5 evidence. Another runtime loses: stock PyTorch on this platform class is 294 ms in Intel's own figures, and the ExecuTorch and ONNX Runtime paths run through the same GPU plugin ([Intel OEP article](https://docs.openedgeplatform.intel.com/dev/OEP-articles/publications/optimizing-pi0.5-lva-model.html)). A newer kernel or compute-runtime has no published compute gain and adds risk the day before a demo. More GPU-plugin settings and further GatedMLP work are measured dead ends.

## Conclusion

Round one found the cheap wins inside the graph and the runtime; round two shows that what remains is a set of model and execution decisions with robot-level consequences. The profile explains why: with launches costing 2.7 µs and the FCs near the memory roofline, latency on this machine is set almost entirely by how many tokens and steps the model runs. That turns optimisation into a training question, which suits a team whose retrain takes 50 minutes. A single cloud session can run a longer three-camera fine-tune, a two-camera variant and a SnapFlow phase in parallel, and the arm then decides between them.

The less comfortable implication is that the latency work has run ahead of the evidence it serves. No variant has moved the arm, the offline metrics reward exactly the mean-seeking behaviour that under-reaches on a robot, and the one external warning about wrong outputs on this GPU is unchecked. An asynchronous 140 ms policy that grasps beats a 90 ms one that has never been run, so the parity check and the first rollout come before any of the ranked items.
